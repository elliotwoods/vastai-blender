## 1. Verdict

The code is not bad in the way that usually justifies a rewrite. Individual functions are careful and full of comments recording real incidents. The pure cores are small and tested: `chunker`, `admission`, `slotController.decide`, `scaling`, `gpuLanes`, `connectRetry`, `pipelinedGet`, `jobClipPlan`, `manifest` parsing, the history SQL against the real `schema.sql`, `frame-domain` and the grade maths. The weak part is the system around them.

1. **Money safety only holds while one Electron process is running, awake and online.** There is no quit handling, no single-instance lock, no liveness check or Vast reconciliation during a session, and no fail-safe on the node. The `'failed'` state quietly means "may still be billing, but no longer metered, capped or counted".
2. **Nothing is validated where data crosses a trust boundary.**
   - A rented host, or any `.blend`, can write arbitrary files on the user's desktop through manifest paths.
   - The renderer runs with `sandbox:false`, and `window.open` goes straight to `shell.openExternal` with no filter.
   - Entering `0` as the chunk size hangs the main process while the fleet keeps billing.
3. **Success is decided by events, not by checking the frames.** Chunks and jobs can finish "complete" with missing frames (one failed manifest read is enough) or truncated ones (the agent sweeps up files left by a crash).
4. **Failures are invisible.** About 25 `emit('alert')` calls, including every "check the Vast.ai console!", go to a channel the renderer never subscribes to. The packaged app writes no log file. About 25 UI actions are fire-and-forget.
5. **The orchestration code is untested and hard to test.** `scheduler.ts` (1272 lines), `nodeManager.ts` (908), `ipc.ts` (761) and `noderunner.py` (1165) are wired together through singletons with import cycles, and none of the rent/destroy/requeue paths have tests. That is why the comments read like an incident log and fixes keep coming back in another path.

**Recommendation: repair it incrementally; do not rewrite it.** The critical bugs sit in about ten places, and each fix can reuse code the repo already has:
- the `media://` path guard at `index.ts:86-91` ✓
- `reconcileOrphans`
- `requeue()` + `missingRanges`
- `agentAlive()`, which is currently never called
- `recoverUnreachable`
- the `node:sqlite` test pattern in `history.test.ts`

A rewrite would throw away the Vast/SSH/Blender edge-case knowledge in those comments and relearn it with real money. The order I'd take: close the money leaks and the path-traversal hole (days), build a fake-Vast/fake-SSH scenario harness around the existing modules (1–2 weeks), then split the large modules with those tests in place.

**Control flows**
1. **Submit.** `SubmitJobDialog` → `job:create` → `createJob` inserts the job, chunk and frame rows in one transaction (`jobs.ts:145-200`) → `scheduler.kick()`.
2. **Scale up.** `scalePolicy` → pure `nodesToRequest` (`scaling.ts:59-79` ✓) → `requestNodes` → `findOffers` → `rentOffer`:
   - INSERT a `'requested'` row, labelled `vastai-blender <id8>`
   - `PUT /asks` → `driveToReady`: poll `showInstance` for up to 8 min, SSH retry for up to 3 min
   - `onReady` (`index.ts`: `provisionBase` → Blender 5.1 → `probeEevee`) → `'ready'`
3. **Dispatch.** `tick()` runs synchronously and calls `run.dispatch()` without awaiting it. Under a per-node mutex, `dispatch` installs the job's Blender version and any extensions and uploads the `.blend`, re-hashing it on every dispatch. It then writes the spec. The agent claims specs in FIFO order.
4. **Progress and downloads.** Two SSH execs per chunk every 5 s: `cat state`, `cat manifest`. Downloads go to `.part`, are verified by size and SHA-256 (the hash comes from the node), renamed into place, then `UPDATE frames/assets` → `asset:added`.
5. **Completion.** On `'done'`: `drain()` → `finish('complete')` if no frames were reported lost → `refreshJobState` works out the job state from chunk states. On `'failed'`: `requeue()` re-splits around the frames already downloaded, up to `MAX_RETRIES=4` (`scheduler.ts:45` ✓).
6. **Money.** `accrueCosts` every 60 s adds `dph/60` to `nodes`, `cost_log`, `usage_log` and `jobs.cost_so_far` for nodes that are not failed or destroyed (`nodeManager.ts:875` ✓). The spend cap is checked only in `scaling.ts:63` ✓ and `requestNodes:583-585` ✓.
7. **Teardown.** A node idle for longer than `idleTimeout` with nothing pending is destroyed. **Quitting does nothing** (`index.ts:421` ✓ only handles `window-all-closed`).
8. **Boot.** `getDb` (migrations) → `nodeManager.init` resumes and **re-provisions** every non-failed node, which kills its agent and in-flight Blender (`provision.sh:61-73` ✓), starts the timers and runs the orphan sweep once → `scheduler.start()` resets stranded chunks to pending with `node_id NULL` and may set the in-memory recovery hold (`669-701` ✓) → `jobClips.catchUp` → `createWindow`.

**Where state lives**

| State | Owner | Notes |
|---|---|---|
| Jobs, chunks, frames, assets, node lifecycle, money series, learned perf | SQLite | Written from 13 modules with raw SQL (#70) |
| What is actually running (`runs`, `byNode`), slots, reservation, recovery hold, `idleSince`, prep mutex, extension cache | Scheduler memory | Allowed to disagree with `chunks.state` (hence `isLive()`) |
| Metrics, energy, blacklist, SSH pool, Octane VNC passwords | NodeManager memory | Lost on restart |
| Settings and secrets | `settings.json` (safeStorage) | No change events, no validation |
| Specs, state, manifests, frames, logs | Node filesystem | Keyed by chunk id, reused across attempts, never cleaned up |
| Mirror of main state; progress, logs, nav, grade | Renderer Query cache, zustand, localStorage | Push-updated |

## 3. Critical and high issues (fix first)

### A. Money safety

**A1. Quitting, closing the window or sleeping leaves the whole fleet billing. CRITICAL**
- **Where:** ✓ `index.ts:421` (only `window-all-closed` → quit). `nodeManager.shutdown()` (`:445`), `scheduler.stop()` and `closeDb()` are never called. Idle scale-down only runs in-process (`scheduler.ts:1221-1231` ✓). There is no node-side fail-safe.
- **Why it matters:** closing the app within the 5-minute idle timeout, or mid-job, or shutting the laptop lid, leaves N GPUs billing until the next launch. No work progresses meanwhile, because the app itself drives dispatch and downloads.
- **Fix:**
  - New `src/main/app/lifecycle.ts`. On `before-quit`, if any node still holds an instance: `preventDefault`, then `dialog.showMessageBox` stating N nodes at $X/h, with *Destroy all & quit* / *Leave running* / *Cancel*.
  - `destroyAll` = `Promise.allSettled(destroyNode)` with a race of about 20 s per node. Then `scheduler.stop()`, `nodeManager.shutdown()`, `closeDb()`, `app.exit()`.
  - Windows: handle `session-end`, and keep the app alive in the tray while nodes exist.
  - `powerMonitor`: warn on `'suspend'`; on `'resume'`, accrue costs and reconcile.
  - Backstop lease: `pollMetrics` touches `control/app_alive`, and `heartbeat_loop` (`noderunner.py:86` ✓) destroys its own instance once the lease is stale and the node is idle, using Vast's per-instance `CONTAINER_API_KEY`. Confirm that key exists and what it can do before relying on it. Do not use `kill 1`, and never send the account key to the node.
- **Effort:** M. **Ids:** #4 #18 #32 #63 #138 #167 #195 #208 (+#45 sleep)

**A2. No single-instance lock. CRITICAL**
- **Where:** ✓ there is no `requestSingleInstanceLock` in `index.ts`. A second process runs `init()`, which re-provisions every node (`nodeManager.ts:367-377` ✓), and that kills in-flight Blender and clears the inbox (`provision.sh:61-73` ✓). `scheduler.start()` then resets chunks that the first process is still rendering.
- **Why it matters:** a double-click on the shortcut kills renders that are already paid for, runs a second scheduler with its own copy of the caps, double-meters spend, and races on the same `.part` files.
- **Fix:** after the `VR_USERDATA` `setPath` block (`index.ts:23-25`), add `if (!app.requestSingleInstanceLock()) { app.quit(); process.exit(0) }`, and focus the existing window on `second-instance`. Headless runs should exit non-zero with a message when the lock is held.
- **Effort:** S. **Ids:** #2 #67 #167 #209 (+#15)

**A3. Destroying a node that is still `'requested'` orphans the instance being created. CRITICAL**
- **Where:** ✓ `destroyNode` (`nodeManager.ts:808-834`) goes straight to `'destroyed'` when `instanceId` is null. `rentOffer` then gets the instance id back from `createInstance` (`620-632`) and calls `driveToReady`, which **returns without destroying** when the state is destroying or destroyed (`650`). The destroy button is shown in every state (`FleetScreen.tsx:270-280`).
- **Why it matters:** the GPU bills until the next launch. The row says `'destroyed'`, so it appears nowhere in cost, cap or History.
- **Fix:** in `rentOffer`, right after `createInstance` resolves: `if (node.state==='destroying'||node.state==='destroyed') { await ensureInstanceGone(instanceId); node.setState('destroyed'); return id }`. Do the same in `driveToReady`'s early return whenever `instanceId` is set. Disable destroy while a node is `'requested'` with no instance id.
- **Effort:** S. **Ids:** #110 #38 #149 #204

**A4. `'failed'` covers both "never rented" and "destroy failed, still billing", and failed nodes are unmetered, uncounted, hideable and not retried during the session. CRITICAL**
- **Where:**
  - ✓ `activeCount` (`nodeManager.ts:534-537`), `activePerHour` (`600-605`) and `accrueCosts` (`875`) all exclude `'failed'`.
  - ✓ The `destroyNode` catch sets `'failed'` (`825-831`), `init` skips failed rows (`374`), and the orphan sweep only runs from `init` (`380`).
  - `destroyInstance` makes a single DELETE attempt and treats 404 as an error (`vastClient.ts:137-139` ✓).
  - Fleet's "hide failed" filter (`FleetScreen.tsx:325`) hides these rows.
- **Why it matters:** one transient DELETE error turns a billing instance invisible to History, the toolbar, the cap and `maxActiveNodes`. The scheduler then rents a replacement.
- **Fix:**
  - A shared billing predicate, `holdsInstance = instance_id != null && !destroyConfirmed` (add a `destroyed_at` column or a `'destroy_pending'` state). Use it in `activeCount`, `activePerHour`, `accrueCosts`, `scalePolicy` and the Fleet filter.
  - One `ensureInstanceGone()` for all five destroy paths (sweep, `driveToReady` catch, `recoverUnreachable`, `destroyNode`, `clearFailed`): retry network/5xx/429 with backoff, treat 404 as success, and confirm with `showInstance`.
  - Run `reconcileOrphans` every 5 minutes from `costTimer`, on `powerMonitor 'resume'`, and after the API key is saved. Skip rows that are still `'requested'` with a NULL instance id, and skip instances younger than about 2 minutes.
- **Effort:** M. **Ids:** #64 #140 #168 #194 #34 #33 #13 #6 #93

**A5. A `createInstance` failure with an unknown outcome is recorded as "not rented", and the batch rents again. CRITICAL**
- **Where:** ✓ the `rentOffer` catch (`633-637`) sets `'failed'`, blacklists the machine and rethrows. `requestNodes` continues for up to 3 failures (`578-595` ✓). `request()` has no timeout and only retries 429 (`vastClient.ts:36-68`, `56` ✓).
- **Why it matters:** a 502/504 or connection reset *after* Vast accepted the PUT leaves a billing instance with no `instance_id`. The next offer is rented straight away, and only the next launch's sweep finds the first instance.
- **Fix:**
  - Classify create errors: an explicit 4xx refusal means not created; network error, 5xx, timeout or non-JSON means unknown.
  - On unknown: stop the batch, keep the row counted as billing, and look up `label === 'vastai-blender '+id.slice(0,8)` via `listInstances` with backoff for about a minute. Adopt the instance (`driveToReady`) or destroy it. Mark the row failed only once the instance is confirmed absent.
  - Never blind-retry `PUT /asks`.
- **Effort:** M. **Ids:** #223 #231 #43 #193

**A6. Nothing checks liveness during a session. CRITICAL**
- **Where:**
  - ✓ The `pollUntilDone` stall watchdog only runs inside `if (state)` (`scheduler.ts:423-484`); a `null` state polls forever.
  - ✓ `agentAlive()` (`provisioner.ts:138`) is never called.
  - ✓ `SshConnection` emits `'disconnected'` (`:106`) with no listener, and `recoverUnreachable` is only reached from `resumeNode` (`769`).
  - The agent refreshes `updatedAt` while Blender is alive, so a hung render never trips the 15-minute watchdog.
- **Why it matters:** if the node's SSH, agent or container dies mid-render, the node stays `'rendering'`. Scale-down requires no runs, so it is never destroyed. The job never finishes, and `eagerFleet` keeps renting.
- **Fix:**
  - A NodeSupervisor inside NodeManager counts consecutive exec/connect failures (from `pollMetrics` and `'disconnected'`). After about 3 (~45 s) it sets `'unreachable'` (which `tick` already excludes) and calls `showInstance`: if the instance is gone or exited, `forgetNode` + `ensureInstanceGone`; otherwise `recoverUnreachable`, which **must re-run `onReady`**, or at least restart the agent and check `agentAlive`, before setting `'ready'` (today it sets `'ready'` directly at `776` ✓).
  - SSH works but the agent is dead: `scheduler.forgetNode`, then `provisionBase`.
  - `ChunkRun` must tell "exec threw" apart from "file absent". Bound consecutive throws. For an absent file past N minutes, check `agentAlive`; do not use a bare timeout, because prefetched specs legitimately wait in the inbox.
  - The agent adds a `lastProgressAt` field, separate from `updatedAt`, so a hung Blender is caught.
- **Effort:** M–L. **Ids:** #17 #36 #52 #77 #139 #169 #192 #90

**A7. The spend cap is advisory. CRITICAL**
- **Where:**
  - ✓ The cap test uses the fleet's current rate, not the rate after the rental: `perHour >= spendCap` (`scaling.ts:63`, `nodeManager.ts:583-585`).
  - The manual "request node" path passes `respectSpendCap:false` (`546` ✓).
  - `activePerHour` excludes failed nodes that may still be billing (`603` ✓).
  - `findOffers` is never given the remaining headroom, although `buildQuery` already maps `maxDphTotal` to `dph_total lte` (`offers.ts:42`).
  - Batch sizing uses placeholder capacities (#227, #237).
  - `hints.ts:33-34` promises the opposite behaviour.
- **Why it matters:** with a $2/h cap and $1.95/h already running, the next rental can be an $8/h multi-GPU box, and manual rentals have no bound at all.
- **Fix:**
  - A pure `capHeadroom(nodes, settings)` using the A4 predicate.
  - In `requestNodes`, pass `maxDphTotal = min(filter, headroom)` and re-check `perHour + offer.dphTotal <= cap` before each `rentOffer`.
  - Manual rentals over the cap need an explicit confirmation.
  - `scalePolicy` should skip when the headroom is below the cheapest plausible offer, to avoid alert spam.
  - Budget each batch by capacity rather than node count, subtracting `planLanes(offer.numGpus, …)` after each rental.
  - Unit tests for all of the above.
- **Effort:** S–M. **Ids:** #5 #16 #35 #65 #94 #144 #158 #172 #211 #227 #237 #113 #199

**A8. Transient Vast errors destroy healthy nodes, and the client has no timeouts or typed errors. HIGH**
- **Where:**
  - `vastClient.ts:36-68` ✓ retries only 429 and has no `AbortSignal`.
  - The API key is also sent in the query string (`:35` ✓).
  - The boot poll (`driveToReady` → `showInstance`) is not retried, so one error lands in the catch, which destroys and blacklists (`715-730` ✓).
  - In `resumeNode`, any error goes to `recoverUnreachable`. That either marks the node ready without provisioning (SSH is fine) or fails it and leaks it (fully offline).
- **Fix:**
  - `AbortSignal.timeout(30s)`, following the pattern at `blendInfo.ts:110`.
  - Retry GET, DELETE and the POST search on network errors, 5xx and 429, with jitter and `Retry-After`. Do not retry `PUT /asks`.
  - A typed `VastError` kind.
  - `driveToReady` tolerates transient errors until its existing 8-minute deadline.
  - `resumeNode` treats "control plane down" differently from "instance gone".
  - Drop `?api_key` once Bearer-only authentication is confirmed.
- **Effort:** M. **Ids:** #39 #236 #33 #193 #168

**A9. Provisioning and prep have no deadline, and an SFTP reset can hang the per-node prep lock. HIGH**

**A10. No warning reaches the user, because nothing subscribes to `alert`. HIGH**

  - Later: a persisted events table.
- **Effort:** S (M with persistence). **Ids:** #6 #93 #111 #171 #191 #210 #234 #12

- **Where:**
  - ✓ `start()` resets stranded chunks to full-range pending. The comment at `671-673` claims "agent skips already-manifested frames", which is false: the agent renders the whole `-s/-e` range.
  - `resumeNode` re-runs `provisionBase`, which kills Blender (`provision.sh:61-73` ✓).

  3. Split `provision.sh base` into *deps* (skipped when a hash stamp of `remote/` matches) and *restart-agent* (only on hash mismatch or a stale heartbeat).
  4. Persist the hold, derived from "any unfinished queued or running job".
  5. Fix the false comments at `scheduler.ts:7-9`, `671-673` and `provision.sh:64-66`.

**A12. Failure loops spend money. HIGH**
- **Where:**
  - One retry budget covers every failure type (`scheduler.ts:45` ✓).
  - `requestNodes` creates 3 failed rows and 3 blacklisted machines per tick, and the blacklist lasts the whole session (`578-595` ✓).

### B. Data integrity

**B1. Chunks and jobs complete without checking the frames arrived. CRITICAL**
- **Where:** ✓ `poll()` swallows exec failures and ignores non-zero exit codes (`frameDownloader.ts:120-133`). `drain()` only returns a "lost" list (`96-118`). On `'done'`: drain, then `finish('complete')` if nothing was reported lost (`scheduler.ts:451-464`). `refreshJobState` looks only at chunk states (`jobs.ts:218`).
- **Why it matters:** frames that were rendered and paid for silently vanish from a job that reports "complete".
- **Fix:**
  - `poll()` returns `{ok}`. `drain()` retries the manifest read with backoff and returns `{ok:false}`, which becomes `finish('failed')`.
  - Before `finish('complete')`, query the frames in the job's frame range with `state != 'downloaded'`. Query by job id and range, not `chunk_id`, because requeue re-points rows. Any hit fails the chunk, and `requeue` re-renders only the gaps.
  - `refreshJobState` reports `'complete'` only when no frame row is still undownloaded.
  - Add `if (this.stopped) return` after every `await drain()`.
- **Effort:** S. **Ids:** #20 #50 #80 #141 #232 #249

**B2. Frames left truncated by a crashed Blender are recorded as good. CRITICAL**

## 4. Systemic themes

1. **"Billing" is not modelled, and safety only exists while the process is alive.** Whether an instance may be charging is inferred from a lifecycle string. `'failed'` hides it. Teardown, reconciliation, metering and caps all rely on one live, awake process running timers.
   - Explains: #4 #18 #32 #33 #34 #45 #64 #66 #138 #140 #150 #167 #168 #194 #208 #223 #231 #256

2. **Implicit state machines with many writers.** Node and chunk states are unconditional UPDATEs from nodeManager (about 17 sites), the scheduler, `index.ts` and a raw UPDATE in the sweep. There are no transition guards and no fencing of stale async writers. Side effects (emit, job state, job clip, node idle) are repeated by hand at each site.
   - Explains: #19 #25 #38 #71 #72 #102 #110 #149 #168 #174 #204 #221 #239 #243

3. **No validation at trust boundaries.** Node → desktop (manifest paths, clip metadata, state JSON), renderer → main (38 channels), `.blend`/`.zip` → main, and Vast API responses are all only type-cast.
   - Explains: #7 #8 #14 #23 #31 #49 #76 #99 #105 #109 #112 #142 #154 #155 #159 #160 #162 #170 #207 #217

4. **Success decided by events, not ground truth.** Chunk "done" is not checked against the frames table, the sweep is not checked against the exit code, clip frame counts are not probed, the job is not checked for scene dependencies, and metered spend is never compared with the Vast balance.
   - Explains: #20 #50 #78 #80 #87 #126 #141 #143 #232 #246 #249 #252 #256

5. **Chunk identity reused across attempts, and per-chunk SSH polling.** Remote paths are keyed by a chunk id whose range changes on every requeue. Each chunk opens two exec channels every 5 s, so channel use grows with chunk count per node. This causes channel exhaustion, stale manifests, racing writers and retry burn.
   - Explains: #24 #54 #55 #79 #145 #179 #181 #182 #242 #243 #245

6. **Silent failure.** The alert channel has no subscriber, there is no log file, IPC calls are fire-and-forget, there are no error states, stub channels promise features that don't exist, and a corrupt `settings.json` silently resets to defaults.
   - Explains: #6 #12 #13 #15 #93 #97 #98 #111 #121 #122 #171 #191 #196 #199 #200 #201 #205 #210 #215

7. **Singletons, import cycles and no seams, so the glue is untested.** `emit` lives in `ipc.ts` (7 domain modules form a cycle with it). Providers are injected through module-global setters. The Vast base URL is hard-coded, and `getDb`/`Date.now` are imported directly. The tested pure cores prove the pattern works; it simply hasn't reached the glue.
   - Explains: #11 #26 #60 #70 #90 #106 #151 #173 #211 #216 #241

8. **The same knowledge is maintained by hand in several processes and languages.** The agent protocol, `hardCap`/`node_ceiling`, frame-count formulas, clip kinds, node-state predicates in UI components, and GPU count/pinning.
   - Explains: #28 #84 #102 #116 #120 #164 #177 #230

**Dependency rule.** `core` ← `services` (through `ports`) ← `ipc`/`app`. Only `app/` and `ipc/` import Electron. Domain modules emit on the bus, and `ipc` forwards bus events to windows. This removes every cycle.

**Source of truth**
- **Instances we may be paying for:** the `nodes` table as a ledger. The row and its label are written before `PUT /asks`, which is the existing strength to keep. A row is billing when it holds an instance or its create outcome is unknown, and no destroy has been confirmed. The Reconciler checks this against `listInstances` every 3–5 minutes and on wake. Caps, cost and UI counts all use `nodeState.ts`.
- **Frames:** the `frames` table. Completion is an invariant query, not an event.
- **Runs:** in memory, keyed by `(chunkId, attempt)`. DB writes are fenced by attempt.
- **Settings:** the file plus a session-only overlay for headless runs, which is never persisted.
- **Renderer:** the Query cache only mirrors main. A separate alert store is fed by replay plus push.

**IPC contract.** Keep `IpcInvokeMap`/`IpcEventMap` and the two-function preload.
- `handlers satisfies {[C in InvokeChannel]: Handler<C>}`, so a missing handler is a compile error.
- A validator per channel inside `handle()`.
- Results as `{ok, value} | {ok: false, code, message}`, because Electron drops custom Error properties.
- The renderer event map is exhaustive.
- Events are coalesced: log lines batched every 200 ms, `node:changed` debounced.
- Replay endpoints (`alerts:recent`, `fleet:cost`) so a new window starts correct.

**Agent protocol.**
- The spec carries `protocolVersion`, `attemptId`, lanes/pin, and either an explicit frame list or `use_overwrite=False`.
- The state echoes `attemptId` and adds `errorKind`, `exitCode`, `logTail`, `preflight`, `engine` and `lastProgressAt`.
- `state/agent.json` holds the ceiling inputs, GPUs, free disk, agent hash and heartbeat. `hardCap` reads these values instead of re-deriving them.
- `control/app_alive` is the lease; `control/<id>.cancel`, or the spec disappearing, means cancel.
- Output directories are per attempt and are garbage-collected after a verified drain.
- Validation happens at `parseManifest`.

**Keep:** manifest-gated verified downloads, atomic spec handoff, the pure cores, the recovery-hold idea, the label-before-create row, `withNodePrep`, `SshConnection`, the `media://` handler, and the renderer's push-first cache discipline (see section 8).

## 8. Strengths to preserve

- **The manifest-gated download protocol.** The agent lists a file only once its size is stable. Downloads land in `.part`, are checked for size and SHA-256, then renamed, so they resume cleanly. The desktop never lists remote directories. It only needs path validation added.
- **Pure, tested policy modules:** `chunker` (`missingRanges`), `admission`, `slotController.decide`, `scaling`, `gpuLanes`, `connectRetry`, `pipelinedGet`, `jobClipPlan`, `manifest`, and `history.ts` tested against the real `schema.sql` through `node:sqlite`. Extend this pattern to the glue code instead of replacing it.
- **Money-safety building blocks:** the node row and label are written *before* `PUT /asks`; `maxActiveNodes` is checked race-free (`nodeManager.ts:582→610` ✓); orphan sweeps are scoped to this profile; every failure path destroys the instance; there is a startup recovery hold.
- **Careful handoffs:** atomic spec writes (tmp → rename), per-writer atomic `write_state`, the `abandoned()`/`retractSpec` checkpoints in `ChunkRun`, and a `tick()` with no awaits (no re-entry).
- **Safe node mutation:** `ensure-optix` stages the libraries, test-renders, then activates them. Provisioning skips work already done by hash. Python always uses argv lists, never `shell=True`. `--python-exit-code`/`GUARD_EXIT`.
- **The typed IPC contract with a two-function preload.** Secrets never cross IPC (only `has*` flags do). Settings are written atomically, secrets use safeStorage, and the `media://` handler supports byte ranges and has a correct path guard.
- **Renderer data discipline:** all query keys in one module; push events folded into the cache; high-rate progress kept out of Query with stable selectors; the preview is a store, not a route; honest, centralised money copy (`hints.ts`); WebGL limited to one surface; `GradeRenderer` and `ClipSyncController` are plain classes that React only mounts.
- **Comments that record incidents.** Turn each "observed live: …" comment into a regression test during the refactor instead of deleting it.

## Phase 0 review follow-ups (deferred)

Open issues from the Phase 0 reviews that Phase 0 did not fix, because a named later item already covers them. Item numbers here are the approved plan's (Phase 0 is 0.0–0.11, Phase 1 is 1.0–1.21), not the §6 numbering above. Where Phase 0 changed docs or copy to say what the code does today, that is noted. Line references were taken when this section was written, and will drift.

**Quit and sleep (plan 1.1).**
- Quitting or sleeping still leaves every node billing. The README's Safety model now gives the manual workaround: set max nodes to 0, destroy each node, wait until no new rows appear, and raise max nodes again before the next render.
- For 1.1's *Destroy all & quit*: `requestNodes` reads settings once, before its awaits (`nodeManager.ts:574`). A scale-up batch already under way (up to 8 rentals, `scheduler.ts:1309`) therefore keeps renting after max nodes drops to 0, or while `destroyAll` runs, and each destroy frees room under the stale cap. `destroyAll` must stop the scheduler and wait out any in-flight batch before it counts the fleet as destroyed. Alternatively, `requestNodes` re-reads `maxActiveNodes` before each rent, next to 1.5's per-rent spend-cap check.

**Mid-session liveness (plan 1.7).**
- `'unreachable'` is still set only by `resumeNode` at launch (`nodeManager.ts:834`). 2.1.0's CHANGELOG fix for "a node that went unreachable mid-render kept billing" covers only that case. Phase 0 added a correction under Unreleased/Changed. A node that dies mid-session is 1.7's.

**Metering and the "actual" rate (plans 1.1, 3.2; Phase 4).**
- Spend is still one minute of the quote per 60 s tick (`nodeManager.ts:943`). Time closed or asleep, and `'failed'` nodes that still hold an instance, are never charged (#66). 1.1 accrues on resume, and 3.2's `CostMeter` accrues elapsed time. Phase 0 corrected the `history.ts` and `schema.sql` comments that called the metered sum true spend.
- The node panel's rate is metered spend ÷ uptime, so it can only confirm the quote (#256). Phase 0 relabelled it *metered ÷ uptime* and made the tooltip say it reads up to about a third high when it first shows. A figure that can disagree with the quote, from balance drawdown against metered spend, is 3.2's balance drift and Phase 4's balance-drift readout.

**Octane (plan 1.18; exec error text also 1.8).**
- There is no VNC button: nothing in the renderer calls `node:openVncTunnel`, and `octaneNeedsManualLogin` is always false (`nodeManager.ts:277`).
